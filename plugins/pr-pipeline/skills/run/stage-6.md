# Stage 6: driving e2e (6b and 6c)

Read when 6a decided that e2e runs. 6a itself, the decision and how it is recorded, is in `SKILL.md`.

**6b. Drive**, in the background while stage 4 reviews (a linked session, or a background subagent), at the route's model and effort, in this order:

1. The profile names an `e2e` skill: run it against the real stack for the lanes the acceptance criteria name. Repo-specific setup (containers, databases, build mounts) belongs to that skill, not here.
2. No `e2e` skill, but `.claude/launch.json` exists: a Browser-pane smoke. `preview_start` its first configuration, navigate to the routes or screens the diff touches, take an after screenshot of every state the criteria mention, and read the console for errors. A before screenshot comes from the base branch when a second preview of it is cheap; otherwise say "after only" in a `note`.
3. Neither: `skipped` with summary `Skipped: no e2e skill or .claude/launch.json in this repo`. Flag it when a criterion needs the running stack.

This pass changes no code and pushes nothing, because the review is reading the same head; tell the e2e skill so, and that it runs no review gate of its own. A lane that fails goes into `<criteriaDir>/e2e/defects.md`: the lane, the criterion, what was seen against what was expected, the screenshot. Close the attempt `done` with the lanes and defects counted (`5 lanes · 2 defects`). Where nothing can run in the background, run stage 4 first and 6b after it.

**6c. Fix and re-drive**, after stage 5's push, only when 6b reported defects or the stage-5 commits change what a driven lane shows. Continue the same e2e session or agent, which still has the stack up: pull, fix the defects it reported, drive the failed lanes and the lanes the stage-5 commits touch again, replace their screenshots, run `lint` and the touched tests, commit, push. Record it as the next attempt of stage `verify` (`running` again), each fix a `did` under its lane. A defect gets two tries. Before the second, write in one sentence why the first fix was expected to work (`Premise: the list is empty because the filter drops archived rows`) and check that against what the lane shows (the console, the network response, the DOM, the database row) before changing code again; record the sentence and what the check showed as a `note`. A defect still open after two tries is a `flag`, and its criterion will be `partial` or `no` at stage 7. 6c also runs when e2e is running for this PR and `security.json` has a posted finding in `authn` or `authz`: it adds a negative lane in which the finding's actor repeats the request against the fixed branch and must be refused, with the response recorded.

Stage 6 never posts a PR comment, and tells the e2e skill not to; its screenshots and table reach the PR only through the proof. Keep screenshots in `<criteriaDir>/e2e/`; Browser-pane screenshots land at `~/.claude/projects/<project>/<session>/tool-results/mcp-Claude_Browser-blob-*.jpg`, so copy the ones you keep. A query-perf route adds a measurement lane (timings or query counts before and after). Cross-repo features start the siblings' branches too and drive the flow across them. Link the published artifact or screenshots to the stage, record the lanes as one `did` list on the closing call, flag any lane you could not drive.
